VITRALLIS LIMINAL WALKING GAME
DESIGN DOCUMENT
Draft compiled from the September 19, 2026 design session

===============================================================================
1. PROJECT SUMMARY
===============================================================================

This is a first-person liminal-space walking game intended to run on the
PocketCHIP through the Vitrallis ecosystem.

The game is intentionally simple in interaction and presentation. Its atmosphere
should come primarily from empty space, repetition, strange spatial layouts,
unusual object placement, and the feeling of being somewhere familiar but wrong.

The game is NOT currently intended to be:
- combat-focused
- puzzle-focused
- collection-focused
- survival-focused
- enemy-driven
- dark or horror-lighting-driven

The initial experience is simply:
- walk
- look around
- explore the environment

Level 1 will be a large Backrooms-inspired interior with:
- yellow walls
- fluorescent ceiling fixtures
- suspended/panel ceiling
- beige/brown carpet
- occasional damp-looking carpet areas
- no enemies
- no collectibles
- no audio

The game should feel spacious rather than claustrophobic.

===============================================================================
2. TARGET PLATFORM AND RENDERING REQUIREMENTS
===============================================================================

Primary initial target:
- PocketCHIP
- Mali-400 GPU using Lima
- 480 x 272 display

Required technology:
- Rust
- SDL2
- OpenGL ES 2.0-compatible accelerated renderer

Rendering requirements:
- hardware-accelerated rendering
- double buffering
- verified VSync / vblank-synchronized presentation
- OpenGL ES 2.0 compatibility as the baseline
- 3D world rendering should be done directly through GLES2 rather than treating
  SDL_Renderer as the 3D renderer
- SDL2 should provide the window, input handling, and OpenGL context
- menus and overlays may also be drawn through the same GLES2 rendering path

VSync must not be considered complete merely because a swap interval was
requested. It should be verified on the physical PocketCHIP by:
- checking the actual swap interval/result where possible
- observing frame pacing
- performing visible tearing tests while turning past strong vertical wall edges

Initial performance target:
- stable 30 FPS at 480 x 272

This is a target, not a guaranteed result.

The renderer should avoid:
- expensive real-time shadows
- dynamic lighting passes
- unnecessary post-processing
- bloom
- camera-driven exposure effects
- per-frame geometry generation
- unnecessary CPU/GPU work

Static environment geometry should be built efficiently and reused.

===============================================================================
3. CORE GAMEPLAY
===============================================================================

The first version has no:
- enemies
- items to collect
- weapons
- inventory
- puzzles
- jumping
- sprinting
- crouching
- audio

The player simply walks through and looks around the environment.

Movement should feel slow enough to encourage observation, but not frustratingly
slow.

Proposed initial movement tuning:
- walking speed: approximately 1.4 m/s
- horizontal look/turn speed: approximately 90 degrees per second
- vertical look speed: approximately 60 degrees per second

These are starting values and should be tuned on the physical PocketCHIP.

Diagonal movement must not be faster than straight movement.

Walking into a wall should allow normal sliding along the wall rather than
causing the player to snag.

Movement and looking inputs must work simultaneously.

===============================================================================
4. DEFAULT CONTROLS
===============================================================================

IMPORTANT:
These controls are intentional and are based on the physical PocketCHIP keyboard
layout. Do NOT replace them with standard WASD.

Movement:
- W = move forward
- A = strafe left
- S = strafe right
- Z = move backward

Looking:
- O = look up
- K = look left
- L = look right
- . = look down

Performance overlay:
- - = toggle CPU / GPU / FPS overlay

The minus key should remain reserved for the statistics overlay unless the design
is intentionally changed later.

The physical PocketCHIP keyboard must be tested for simultaneous-key behavior,
especially combinations of movement and look controls.

===============================================================================
5. CAMERA
===============================================================================

Proposed starting camera values:
- eye height: approximately 1.6 m
- horizontal field of view: approximately 75 degrees

The player remains grounded on the floor regardless of vertical look direction.

Initial camera presentation should avoid:
- head bob
- camera shake
- weapon/hands model
- crosshair

The environment itself should dominate the screen.

===============================================================================
6. MAIN MENU AND GENERAL UI
===============================================================================

The game starts at the main menu.

Main menu:
- Level Select
- Settings
- Exit

The build/game version must be shown in the bottom-left corner of the main menu.

Proposed menu background:
- a static view of the game environment
- no need for a continuously animated 3D menu camera

No invented slogans, taglines, or unnecessary branding text are required.

===============================================================================
7. LEVEL SELECT
===============================================================================

The Level Select screen should show:

Level 1

Under construction
Under construction
Under construction

Back

Only Level 1 is playable initially.

The "Under construction" entries should:
- visibly appear unavailable/disabled
- not launch a level when selected

More levels can be added later without redesigning the menu structure.

===============================================================================
8. SETTINGS
===============================================================================

The Settings menu must allow users to rebind all movement and look controls:

- forward
- strafe left
- strafe right
- backward
- look up
- look left
- look right
- look down

Settings should also provide:
- restore default key bindings
- adjustable look speed

Key bindings should persist between launches.

Rebinding behavior should:
- show the current assigned key
- clearly enter a "waiting for new key" state
- handle binding conflicts explicitly
- avoid silently creating confusing duplicate bindings

Proposed menu navigation independent of gameplay bindings:
- W / Z or arrow keys = change selection
- Enter = confirm
- Esc = back / pause

Menu navigation should remain usable even if gameplay controls are rebound.

===============================================================================
9. PAUSE MENU
===============================================================================

Proposed pause menu:
- Resume
- Settings
- Return to Main Menu

No gameplay HUD is required while walking other than the optional stats overlay.

===============================================================================
10. CPU / GPU / FPS OVERLAY
===============================================================================

Pressing the - key toggles a compact performance overlay.

Default state:
- hidden

Placement:
- along the top of the screen
- preferably top-left
- small enough not to obstruct normal exploration

Example presentation:

CPU 42%   GPU 61%   FPS 30

The actual values must be measured, not invented.

CPU:
- report overall CPU utilization in a lightweight manner

GPU:
- use real GPU utilization/activity information where available
- do not use GPU clock frequency as a fake utilization percentage
- if meaningful utilization data cannot be obtained, show GPU N/A

For Lima/Mali hardware, real devfreq activity data should be used when available.

FPS:
- use actual rendered frame timing

The displayed values do not need to update every frame.
A low-rate update such as roughly twice per second is appropriate.

Text should be cached rather than rebuilt unnecessarily every frame.

===============================================================================
11. LEVEL 1 OVERVIEW
===============================================================================

Level 1 is a large, empty, Backrooms-inspired liminal space.

Visual components:
- yellow walls
- fluorescent fixtures
- suspended/panel ceiling
- muted beige/brown carpet
- occasional dark/damp-looking carpet regions
- broad, bright, flat lighting
- simple geometry

The space should not rely on darkness for mood.

The environment should feel:
- bright
- empty
- repetitive
- quiet
- spacious
- slightly wrong
- unnatural without being overtly threatening

There are no enemies or objectives.

===============================================================================
12. LEVEL 1 FLOOR PLAN
===============================================================================

The uploaded floor-plan drawing from the design session is authoritative.

Do not redesign it into a different maze.

Interpretation rules:
- the outer outline is the enclosing room boundary
- the outlined rectangles are solid wall footprints
- those walls extend from floor to ceiling
- overlapping rectangles form solid intersecting/cross-shaped wall structures
- the open central area should be preserved
- the three major cross-like wall structures should be preserved
- the upper-left partition arrangement should be preserved
- the tighter lower-right partition/maze arrangement should be preserved
- openings shown in the drawing should remain open
- the red start marker represents the player spawn
- the red marker and "start" label are not visible in-game

The exact physical dimensions of the layout can be tuned while preserving the
drawn proportions and arrangement.

Earlier proposed starting footprint:
- approximately 32 m wide
- approximately 30 m deep

These dimensions are not locked.

Initial spawn facing direction was not explicitly defined by the drawing.
A reasonable initial implementation may face the player toward the structures in
the upper half of the map, but this can be adjusted later.

===============================================================================
13. CEILING HEIGHT
===============================================================================

The earlier 2.7 m idea was rejected as potentially too claustrophobic.

Current agreed starting ceiling height:
- 3.5 m

Optional comparison during physical testing:
- 4.0 m

Level 1 should initially use a single consistent ceiling height rather than
multiple height zones.

The room height should be defined in the level data.

Example:

"room": {
  "width": 32,
  "depth": 30,
  "height": 3.5
}

Floor-to-ceiling walls should automatically use the room height.

Ceiling-mounted objects should follow the ceiling height while preserving their
intentional offsets.

Floor-standing objects should not move merely because the ceiling height changes.

===============================================================================
14. LIGHTING DIRECTION
===============================================================================

The desired lighting style is bright, simple, flat, and inexpensive.

Visual reference:
- the general feel of older Source-engine baked/static lighting

Important:
The atmosphere should come from the empty space and environment design, NOT from
the level being dark.

Bright is good.

The first version does NOT need:
- fancy dynamic lighting
- real-time shadows
- bloom
- per-light calculations
- sophisticated light baking
- flickering lights
- exposure adaptation
- dramatic dark corners

A full lightmap baking system is not required initially.

Recommended first-version approach:
- textured surfaces
- fixed/static brightness or color multipliers
- subtle fixed directional differences between wall faces if useful for depth
- no dynamic per-light illumination

The purpose of any subtle face shading is only to keep corners and intersecting
geometry readable.

The game should not make every surface so uniformly identical that spatial depth
is lost, but the result should remain bright.

===============================================================================
15. CEILING LIGHT FIXTURES
===============================================================================

Level files need explicit ceiling-light placement.

The lights are important visual objects even before they become real lighting
sources.

A level should contain a section such as:

"ceiling_lights": [
  {
    "fixture": "core:fluorescent_panel_01",
    "x": 6,
    "z": 4,
    "rotation_degrees": 0
  },
  {
    "fixture": "core:fluorescent_panel_01",
    "x": 12,
    "z": 4,
    "rotation_degrees": 90
  }
]

For normal ceiling-mounted lights:
- x and z specify the fixture center on the floor plan
- the fixture can automatically use the room ceiling height
- rotation controls its direction/orientation

Example fixture codes:
- core:fluorescent_panel_01
- core:fluorescent_twin_01
- core:fluorescent_square_01

A fixture definition may contain:
- model/geometry
- dimensions
- surface material
- apparent brightness
- default orientation information

Initial behavior:
- ceiling lights are visible fixtures
- they do NOT need to dynamically illuminate nearby geometry
- moving/removing a fixture does not need to change room brightness yet

Brightness can initially control the appearance/emissive look of the fixture
itself.

Future lighting systems may later use the same placement information for baked
illumination.

===============================================================================
16. INTENTIONAL INTERSECTIONS AND CLIPPING
===============================================================================

Intentional object/environment intersection is ALLOWED.

This is a deliberate part of the game's liminal visual language.

Do NOT automatically treat the following as placement errors:
- walls intersecting walls
- props intersecting walls
- lights intersecting walls
- lights partly entering the ceiling
- props clipping into floors
- props clipping into other props
- unusual floating placements
- deliberately impossible spatial arrangements

The game/editor should NOT automatically:
- lift objects onto the floor
- separate overlapping objects
- snap objects away from walls
- "fix" intersections
- carve automatic holes around intersecting props
- reject a level solely because geometry looks physically impossible

Snapping may eventually exist as an optional editor aid, but saved positions must
be respected exactly.

===============================================================================
17. FUTURE PROP PLACEMENT
===============================================================================

Future levels may contain props such as chairs.

Props should support true 3D placement, including vertical offsets.

Suggested coordinate convention:
- x = horizontal world position
- y = vertical world position
- z = depth world position

For a floor-standing prop with its origin at the base center:
- y = 0.0 means its base is on the floor
- y = -0.25 means it is sunk 25 cm into the floor
- y = 0.5 means its base floats 50 cm above the floor

Example:

{
  "asset": "core:chair_01",
  "x": 8,
  "y": -0.25,
  "z": 12,
  "yaw_degrees": 20,
  "collision": "solid"
}

This should render the chair partially buried in the carpet.

Placement and collision are separate concerns.

Possible collision modes:
- solid
- none

If an object is moved, rotated, sunk, or floated, any enabled collision shape
should follow that actual placement.

Allowing scenery to intersect does NOT mean the player has noclip.

===============================================================================
18. SHAREABLE / COMMUNITY LEVEL SYSTEM
===============================================================================

The game should eventually allow other people to create and share their own
levels.

The level format should therefore be:
- simple
- readable
- data-driven
- editable without recompiling the game
- safe to load
- easy for other tools/editors to generate

Recommended initial format:
- JSON

Official levels should use the SAME loader and SAME level format as community
levels.

Do not hard-code Level 1 into Rust in a special way.

This is important so that:
- the official game exercises the public level format
- future community levels do not use a second-class code path
- a future editor can write the same format directly

===============================================================================
19. LEVEL FORMAT PHILOSOPHY
===============================================================================

The level should describe WHERE things are.

The material/asset catalogs should describe WHAT they look like.

This separation allows:
- changing textures without changing geometry
- adding new materials without rebuilding level layouts
- reusing the same wall geometry with many appearances
- future community content

Use human-readable permanent identifiers rather than fragile numeric indexes.

Good:
- core:wallpaper_yellow_01

Avoid:
- texture: 17

IDs should not change when new materials are added.

===============================================================================
20. MATERIAL SYSTEM
===============================================================================

Examples of permanent material codes:

- core:wallpaper_yellow_01
- core:wallpaper_stained_01
- core:carpet_beige_01
- core:carpet_damp_01
- core:ceiling_panel_01
- core:ceiling_stained_01

A "material" can represent more than a raw image.

A material definition may later include:
- texture image
- tint
- repeat/tile size
- simple rendering flags
- other lightweight appearance data

Adding a normal new wallpaper or carpet should usually require:
- adding the image/resource
- adding a material-catalog entry

It should NOT require adding new Rust code merely to expose another ordinary
texture.

Material IDs should be permanent.

===============================================================================
21. MATERIAL INHERITANCE / OVERRIDES
===============================================================================

Recommended precedence:

1. individual surface override
2. object-level material
3. level default material

This allows creators to:
- change the entire level's default wallpaper
- change one complete wall
- change only one side of a wall

Example defaults:

"defaults": {
  "wall": "core:wallpaper_yellow_01",
  "floor": "core:carpet_beige_01",
  "ceiling": "core:ceiling_panel_01"
}

Example wall with one face overridden:

{
  "x": 14,
  "z": 12,
  "width": 0.35,
  "depth": 5,
  "faces": {
    "east": "core:wallpaper_stained_01"
  }
}

===============================================================================
22. SIMPLE GEOMETRY FORMAT
===============================================================================

Initial geometry should be deliberately basic.

For Level 1 and early community levels, rectangular wall footprints are preferred
over requiring creators to provide arbitrary 3D meshes.

A wall entry can describe:
- x position
- z position
- width
- depth
- optional material
- optional per-face materials

Walls extend floor-to-ceiling by default.

Example:

"walls": [
  {
    "x": 4,
    "z": 6,
    "width": 6,
    "depth": 0.35
  }
]

A room can define:
- width
- depth
- height

The room itself supplies:
- outer boundary
- floor
- ceiling

Internal walls are added separately.

===============================================================================
23. FLOOR MATERIAL PATCHES
===============================================================================

Level 1 needs occasional damp-looking carpet areas.

These should initially be appearance regions rather than physical puddles.

Example:

"floor_patches": [
  {
    "x": 7,
    "z": 9,
    "width": 2,
    "depth": 1.5,
    "material": "core:carpet_damp_01"
  }
]

The patch should alter the floor appearance in that area.

It should NOT:
- automatically create water
- add reflection
- add an extra overlapping floor slab
- affect player movement unless intentionally extended later

===============================================================================
25. LEVEL PACKS AND CUSTOM CONTENT
===============================================================================

Simple levels that only use built-in resources should be shareable as a single
JSON file.

For community levels that include custom textures/resources, use a packaged
archive format such as ZIP.

Example:

my-level.zip
|
+-- level.json
+-- materials.json
+-- textures/
    +-- wallpaper.png
    +-- carpet.png

Built-in resources should use:
- core:...

Custom level-pack resources may use a namespace such as:
- pack:...

Example:
- pack:wallpaper_blue_01

A downloaded level pack should NOT be able to replace or redefine core materials
globally.

Its custom material IDs should remain scoped to that pack.

===============================================================================
26. LEVEL LOADING AND PERFORMANCE
===============================================================================

JSON should be parsed at load time, not repeatedly during rendering.

At load time:
- parse the file
- validate basic structure
- resolve material IDs
- resolve fixture IDs
- build internal geometry
- build collision geometry
- convert long string IDs into efficient internal handles
- upload textures/resources as appropriate

The render loop should use resolved internal data rather than repeatedly:
- parsing JSON
- searching strings
- rebuilding static geometry

===============================================================================
27. LEVEL VALIDATION
===============================================================================

Validation should focus on malformed or dangerous data, NOT on whether the level
looks physically realistic.

Valid reasons to reject or warn:
- malformed JSON
- unsupported format_version
- invalid numeric values
- missing required fields
- missing referenced asset/material
- unreasonable resource usage
- unsafe archive paths
- archive expansion limits exceeded
- impossible memory requirements
- corrupt texture/resource data

NOT valid reasons to reject:
- a chair is buried in the floor
- a light intersects a wall
- two props overlap
- a wall intersects another wall
- a prop floats in the air
- an object clips through the ceiling

The creator controls the visual arrangement.

Community/downloaded levels should remain data-only.

Do not permit downloadable levels to contain or execute:
- scripts
- executables
- arbitrary native code
- custom shader programs

At least in the initial community-level design.

===============================================================================
28. FORMAT VERSIONING
===============================================================================

Every level should have a format version.

Example:
- "format_version": 1

Increment the level format version when the STRUCTURE or SEMANTICS of the file
format change.

Do NOT change the format version merely because:
- a new wallpaper is added
- a new carpet texture is added
- another built-in fixture is added
- another ordinary asset is added to a catalog

A level that references a missing material should produce a clear error or
fallback behavior rather than silently loading unpredictably.

32. IMPORTANT DESIGN PRINCIPLES
===============================================================================

1. SIMPLE GEOMETRY IS A FEATURE
The PocketCHIP's limitations should contribute to the aesthetic rather than be
hidden.

2. EMPTY SPACE IS THE EXPERIENCE
Do not compensate for emptiness by filling the level with enemies, items, or
objectives.

3. BRIGHT DOES NOT MEAN SAFE
The environment can feel liminal and uncomfortable while remaining clearly and
evenly visible.

4. COMMUNITY LEVELS ARE FIRST-CLASS
Official levels and community levels should use the same data-driven system.

5. MATERIAL CODES ARE STABLE
Creators should be able to change the appearance of surfaces by changing readable
material IDs.

6. CLIPPING CAN BE ART DIRECTION
Do not "fix" strange prop/wall/floor intersections unless specifically requested.

7. PERFORMANCE COMES BEFORE VISUAL COMPLEXITY
The PocketCHIP should receive a stable, responsive experience before expensive
effects are considered.

8. VERIFIED VSYNC MATTERS
Tearing is particularly distracting in a first-person game with strong wall
edges. Double buffering and actual synchronized presentation are requirements.

===============================================================================
APPENDIX A. CORE PROP ASSETS (IMPLEMENTED)
===============================================================================

The open questions above about the prop/asset format, texture dimensions, the
material model, prop collision and the initial prop library are settled by the
shipped core prop pack:

- registry: assets/props/props.json, shared by the game (src/loader.rs) and the
  level editor (level-editor/js/props.js); there is only one prop list.
- models: assets/props/models/*.glb, generated from primitives by tools/props
  (pure Python, no Blender) and reproducible with `python3 tools/props/build.py`.
- scope: twenty core props - eight furniture, six appliances, crate and
  cardboard box, plant/rug/floor lamp/television - plus `spooner-man`, a
  low-poly tuxedo cat built from the same toolkit and registered as an ordinary
  static prop. No variants, no interactive props.
- format: self-contained GLB, one scene/node/mesh/primitive/material, POSITION +
  TEXCOORD_0 + COLOR_0, one embedded PNG (64x64 or 128x128, 256x256 hard cap),
  triangles only, no extensions, no skins, no animation.
- material model: diffuse texture multiplied by baked vertex colour (per-face
  shading and contact darkening), unlit, straight through the existing GLES2
  shader. No normal/metallic/roughness/AO maps, no alpha.
- budgets: 50-500 triangles preferred per ordinary prop (1500 hard ceiling),
  one draw call per distinct prop model per level; instances of one model share
  a decoded mesh, one CPU copy and one GPU texture.
- collision: the catalogue's axis-aligned box, never the render mesh; the
  level's per-placement `solid` flag decides whether it blocks the player.
- convention: 1 unit = 1 metre, Y up, origin at the floor-contact centre, +Z is
  the prop's front; the bounding box matches the catalogue `size`.
- documentation: assets/props/README.md (asset rules) and
  tools/props/README.md (toolkit and commands).
- validation: `python3 tools/props/build.py --check` for the files and the Rust
  test `props::tests::shipped_prop_assets_match_the_catalogue_and_budgets` for
  the catalogue, budgets, scale, origin and UVs.
- fixtures: assets/levels/prop_showcase.json (every catalogue prop, including
  deliberately sunk and overlapping placements) and
  assets/levels/prop_stress.json (repeated-prop load for batching and memory).
