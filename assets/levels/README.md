# Shipped levels

Five compiled packages are bundled with the game: `places_demo`, `model_zoo`,
`movement_test`, `lantern_hollow` and `winter`. They are discovered at startup,
appear in the Level Select menu, and are copied by `tools/package.sh`. Boot straight
into one with `PLACES_LEVEL=places_demo` or `PLACES_LEVEL=model_zoo` (a bundled
level shows its `id`, the display name works in the menu).

`assets/levels/` is the shipped-level directory: every `*.placesmap` here is
discovered and packaged. Nothing here is hard-coded, so adding a package adds a
menu entry and removing one removes it. Drop-in user packages live in `levels/`
at the repository root and are discovered alongside the bundled levels. The
release script also copies any compiled drop-in packages present when exporting;
`tests/fixtures/levels/` holds the engine regression fixtures
and is never packaged.

The `.json` files here are the **authoring sources**. They are kept so authors
can edit and recompile them; the player never reads them. Every source maps to
its sibling package:

```sh
./target/release/places-compile build assets/levels/places_demo.json
./target/release/places-compile build assets/levels/model_zoo.json
./target/release/places-compile build assets/levels/movement_test.json
./target/release/places-compile build assets/levels/lantern_hollow.json
./target/release/places-compile build assets/levels/winter.json
```

A build reuses the existing package when the source and its asset identities are
unchanged; pass `--force` to rebuild. See `docs/PACKAGE_FORMAT.md`.

## The shipped levels

| id | name | what it is |
| --- | --- | --- |
| `places_demo` | Places Demo | **The showcase.** One continuous route through everything the project does: office → doorways and windows → red stair hall → empty pool → two steps up → quiet corridor → Home archway, living area, pool deck and upper balcony. | `model_zoo` | Model Zoo | **The catalogue showroom.** A large, well-lit pool hall that displays every registered placeable model at least once, plus the pose, route, switch, floating-prop, sign and mount demonstrations. | `movement_test` | Movement Test | Controller diagnostics for steps, slopes, jumps, water and ladders. Maintained authoring source, exercised by the real movement tests. |

### Lantern Hollow

`lantern_hollow.json` is generated by
`python3 tools/levels/build_lantern_hollow.py`; `--check` proves deterministic
source output. Its sibling compiled package is discovered by the same Level
Select and packaging flow as every other package in this directory.

After a normal compiler build, launch with
`PLACES_ASSET_ROOT="$PWD" PLACES_LEVEL=lantern_hollow ./target/release/places`
from the repository root. Four furnished cottages face the road; their doors
start open and toggle with **E**. Five forest paths converge on seven seated
skeletons around an animated campfire. A circular pond lies to the west,
three existing sheet-ghost cats drift in the forest, and visible rock faces
with closed road gates enclose the map. There are no cars.

The generator owns only its JSON; it does not bake lightmaps or introduce
rendering exceptions. `tests/test_lantern_hollow.py` checks authoring contracts,
and `src/showcase_audit.rs` drives the real fixed-step player controller across
all interiors, doors, trails, the pond and boundary jump challenges. Native
visual acceptance and package validation remain separate checks.

### What Places Demo demonstrates

The demo is the technical reference for the door and effect authoring contract:

- `hall_door` — a white painted interior door (`kind: interior`), manually
  interactable, with the wall opening authored separately on its wall.
- `hall_switch` — a `home:wall_switch` prop carrying `interactable` and
  `animation` components; its `on: interact` binding plays the lever clip and
  toggles `hall_door` (`toggle_animation` and `toggle` in one action batch).
- `sauna_door` — a sauna leaf (`kind: sauna`): cedar stiles and rails around a
  clear glass panel, with a wooden round handle.
- `study_door` — an externally controlled door (no `interactable` component and
  no binding) that starts open and is moved only by map actions, so it is never
  an interaction target; the `study_door_approach` and `study_door_return`
  trigger volumes drive it from either side.
- `sauna_steam_a` / `sauna_steam_b` — `effects[]` steam emitters inside the
  sauna; presentation-only, bounded particle plumes. They start **off** and the
  second wall switch (`sauna_steam_switch`, on the south wall) toggles them in
  one press: two mutually exclusive `state` bindings hold the room filled or
  clear, and the press never touches the lamp switch or a door.
- `sauna_hall_door` — an additional sauna leaf in the formerly open corridor
  doorway (wall 17), hinged on the north jamb and swinging into the sauna clear
  of the benches; the pool-side `sauna_door` is unchanged.
- `pool_hot_tub` / the circular `water` volume — a genuinely circular hot tub
  on the pool deck's north-west corner: a joined shell over a 30-strip
  inscribed recess, with a disc water volume of the same radius so membership,
  the collision rim and the drawn surface are one circle, plus gentle surface
  emitters independent of the sauna switch.
- `night_guard_a/b/c` and the `night_guard_wake` sequence — three waiting
  pumpkin-head skeletons inside the night-route house; the `night_guard_zone`
  volume starts their remove-head clip together once per entry.
- the windows and the transfer grille — `glass` panes that also author
  `"solid": true`, so the pane blocks the player as well as reading transparent.

`levels/level0_pit.json` is the reference for a volume-driven door: the
`pit_gate` leaf is externally controlled and driven by the `pit_gate_approach`
(open) and `pit_gate_passed` (close) trigger volumes.

### Regenerating the Model Zoo

```sh
python3 tools/levels/build_model_zoo.py              # write assets/levels/model_zoo.json
python3 tools/levels/build_model_zoo.py --check      # fail if the file is stale
python3 tools/levels/build_model_zoo.py --stats      # coverage and layout summary
python3 tools/levels/build_model_zoo.py --workers 8  # bounded inspection workers
```

The tool reads `assets/catalog.json`, inspects each model's real bounds and
animation envelope (cached under `cache/`, invalidated per model by size and
mtime), lays the displays out deterministically and writes one canonical level.
Adding a catalogue entry adds a display; removing one removes it; no other
instance is renumbered. Serial and parallel runs are byte-identical.

## Capacity fixtures

`tests/fixtures/levels/capacity_beyond_former_limits.json` and `capacity_dense.json` are the
generated stress fixtures for the raised level limits. They are regenerated by
`tools/levels/build_capacity_fixtures.py` (with a `--check` mode) and are the
witness set for material-index/source-capacity and dense-instance contracts. They are not
packaged and do not appear in the Level Select menu; run one with
`./target/release/places --check-geometry --level tests/fixtures/levels/capacity_dense.json`
or compile it explicitly to a `.placesmap` in an isolated state root to boot it.
The retired `capacity_sparse.json` is not a maintained source.

The fixtures live in `tests/fixtures/levels/`, outside the shipped content, so
they do not appear in a packaged game's Level Select menu. They are
load-bearing: each one is named by an automated test or a documented manual
check.

| `capacity_dense` | Capacity: Dense Content (dev) | The `zoo_audit` scale contract: 5000+ placements over a fixed historical 48-model collision/instance witness, 100+ fixtures and 16+ routed entities. Model Zoo owns complete current catalogue coverage. |
| `pool_showcase` | Pool Showcase | The Pool-family geometry and collision checks in `src/render/tests.rs` and `tests/test_package.py`. |
| `vertical_diagnostic` | Vertical Diagnostic | The vertical-geometry fixtures: an elevated room reached by a region staircase, a walkable recess and a blocked deep recess, a gable room with eave and ridge fixtures, RGB-lit corners, decals. Used by the loader and renderer geometry tests. |

| `home_showcase` | Home Showcase (dev) | The Home theme and every generic architectural piece: four rooms (living room, hall, kitchen, bedroom), a split-level platform reached by a staircase and a ramp, an archway, a knee wall, columns, guardrails, thresholds, baseboards, both hardwoods, carpet, tile and both ceilings. `prop_showcase` and `prop_stress` are **generated**: running
`python3 tools/levels/build_fixture_levels.py` overwrites them; the two
`capacity_*` fixtures are generated by
`python3 tools/levels/build_capacity_fixtures.py`. Change the generator, not the
JSON. `outdoor_kit_showcase` and `lighting_quality` also have dedicated generators.
Other fixtures retain their historical or authored control semantics; see the
[complete Stage 7 inventory](../../docs/art-style/stage7/content-inventory.json)
for each source's ownership and validation commands.

`home_showcase` is the level to boot when working on the Home theme or the
generic architectural pieces. It is a fixture rather than shipped content, so it
does not appear in a packaged game's menu. Compile it into an isolated state
root to review it without replacing the distinct historical local Home source:

```sh
mkdir -p /tmp/places-home-review/levels
./target/release/places-compile build tests/fixtures/levels/home_showcase.json \
  --out /tmp/places-home-review/levels/home_showcase.placesmap
PLACES_ASSET_ROOT="$PWD" PLACES_STATE_ROOT=/tmp/places-home-review \
  PLACES_LEVEL=home_showcase ./target/release/places
```

## Packaging

The packaged content ships every compiled package in `assets/levels/`, plus any
compiled drop-in packages present in `levels/` during export. All resolve the complete catalog: every model, texture and
material in `assets/catalog.json` is available to `Places Demo`, the Model Zoo,
the engine and user-created levels. To find "where is every asset", read the
catalog-driven Model Zoo: it is generated from `assets/catalog.json`, so it
cannot fall behind it.

Regenerating the zoo means regenerating the JSON source with
`tools/levels/build_model_zoo.py` and then recompiling the package with
`places-compile build`, exactly like any other edited map.

### Winter

`winter.json` is generated by `python3 tools/levels/build_winter.py` (`--check`
checks deterministic output). Build its sibling package with
`./target/release/places-compile build assets/levels/winter.json --workers 12`.
Launch with `PLACES_ASSET_ROOT="$PWD" PLACES_LEVEL=winter ./target/release/places`.
The snowy settlement has three enterable cottages, a raised lodge terrace with
stairs/ramp, a physically walkable ice pond with its authored traction, conifer forest,
rock boundaries and warm lamps. Doors start open and toggle with **E**.

The completed static snow kit, winter namespace and reuse contracts are documented
in `assets/environment/winter/README.md`. `src/game/tests/winter.rs` checks real
controller traversal and collision; `tools/bench/capture_winter.py` captures
native game views. See `docs/WINTER_FOUNDATION.md` for validation and evidence.
