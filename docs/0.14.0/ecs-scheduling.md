# ECS scheduling in Places

**Keep the current loop for 0.14.0.** Borrow Bevy’s discipline of declaring reads, writes, and commit points. Don’t add an executor or ECS dependency. Later agents already observe earlier agents’ accepted movement, so dispatching whole actor updates together would change gameplay. There is one smaller batch worth profiling first: the visibility probes made before Luau runs.

This is source research for [#47], related to the already closed [#31]. The Mac checkout, remote-tracking ref and live `origin/0.14.0-dev` all matched Places `a49841df70c07df38e5180cb53330ebcc42e5197`. The upstream `v0.20.1` tag resolved to Bevy `a0577b5c6a7b208719dd761c5c6a7a539e472a97`. **Performance unmeasured.** No binaries, maps, benchmarks, or runtime changes were produced.

## What has to stay ordered

| Phase | Reads, writes, and observable order |
| --- | --- |
| Player and contacts | The native frame samples item obstacles, then moves the player. Doors advance before fixed player commands, which query live item/held-body contacts and record the accepted path. `EntityWorld::tick` consumes the resulting feet/eye, collision data, and nav mesh, then routes/fades advance. The later fixed Rapier item step is distinct from those player commands. [Player input][input], [movement][movement], [contact coupling][contacts], [world handoff][world] |
| Timers, actions and Luau | The world samples pre-script visibility, opens a shared VM budget, and may resume a pending terminal binding before automatic callbacks. Callback actions can change live state before timers and sequences. Timer expirations enqueue events, with one-shots using terminal dispatch. The subsequent encounter, actors, explicit moves and lifetimes can produce more effects before the event pump. Preserve FIFO admission and the first-child slot across a terminal yield, once/cooldown commits, reset short-circuits, and stale-subject rejection. Limits include 4,096 queued events, 256 processed per tick, and shared Luau call/action/time budgets. Luau’s build enables `send`, but mutable VM/module state, world-backed reads and ordered actions still belong to the gameplay caller. [Tick][tick], [timers][timers], [dispatch][dispatch], [binding commit][binding-commit], [FIFO][fifo], [VM][vm], [Places manifest][places-manifest] |
| AI and navigation | Ordinary AI consumes target/stimulus snapshots, scripted ownership, item observations and door state/version. It rotates its first agent, reuses path scratch, and shares reservations, alerts and already-published actor positions. Route search reads the nav grid and a door-state view, writing scratch and a path, but choosing/accepting that path and applying door, task, motion and event effects is part of the ordered AI update. Feltlings replace each collider before the next Feltling runs. Tall Guests then consume Feltling prey/poses, update their own collider list in order, and can capture prey and emit catches. Freezing all actors at the start would change those reads. [AI input/effects][ai-input], [AI loop][ai-loop], [path query][nav], [Feltlings][feltlings], [Tall Guests][guests] |
| Rapier, trigger paths and command commits | The app handles interactions and drains world commands before the fixed item step. Rapier receives the accepted player context and current doors, steps water/contacts/ragdolls, and publishes item poses, impacts and substep paths. The app observes bodies/releases, merges accepted player and item paths into chronological trigger crossings, and dispatches their actions before the second ordered command drain. Accepted level changes can stop a drain. Moving triggers before the item step or committing results by worker completion order changes the same-frame contract. [Frame loop][frame], [command passes][commands], [command consumer][consumer], [Rapier][rapier], [trigger dispatch][triggers], [crossing publication][crossings] |
| Pose, render and audio | Gameplay/controllers own live transforms, cues and creature poses. Rapier owns physical/ragdoll poses. The renderer consumes entity frames and advances ordinary character animation before posed contacts/socket attachments, then publishes dynamic visibility and syncs lighting/skinning against that same frame for props, characters and water. One-shot completions feed back to entity bindings and sequences. The published camera drives listener mix, while audio resolves live source positions and drains guest cues, physical impacts and audio-start observations. Impacts feed AI even if a voice is refused. Keep SDL events/window, renderer install/device/queue/surface/present, and game-side audio controls on their current caller across desktop backends. SDL’s audio callback already owns output mixing. [Creature frames][creature-frames], [pose handoff][pose], [GPU publication][gpu], [audio handoff][audio], [impact feedback][impact], [SDL callback][audio-callback], [startup][startup] |

## One candidate, only if the profile warrants it

Places already uses a bounded Rayon pool with small batches inline and a join before publication. Examples include CPU fallback skinning before ordered uploads, water immersion before ordered force application, and feature-gated Rapier solver work with an explicit serial fallback. The separate loader uses capacity-one channels, cancellation and current-request checks, not a simulation scheduler. [Runtime pool][pool], [skinning][skinning], [water][water], [solver][solver], [loader][loader]

The **pre-script visibility batch** has independent outputs. When a VM is enabled, each ordinary AI agent uses the same player eye, walls, resolved door leaves and item solids, plus its own torso input. The probes produce booleans, with no world effects other than the caller inserting visible handles. Both Luau and AI can read the resulting membership. There is a real implementation obstacle: `CollisionIndex::for_each_ray(&self)` mutates shared stamps and a reusable scratch buffer through `Cell`/`RefCell`. It cannot be shared as-is. Only if this phase is hot, prototype separating immutable index data from private traversal scratch in the collision owner. Preserve the existing traversal, filtering and fallbacks. Use coarse contiguous chunks on the existing pool, with bounded reusable scratch per chunk and one result slot per actor. Keep small batches inline. Avoid cloning the index or locking it per ray. [Probe site][tick], [LOS query][los], [index and scratch][index], [Luau reader][luau-reader], [AI reader][ai-input]

Join within the same frame and commit membership in input order before any callback. Workers do not write entities, dispatch actions, call APIs or hold scene leases beyond the join. There is no asynchronous cancellation path to add: one in-flight batch and no inter-frame queue mean reset, unload or shutdown on the owner cannot race its results. Keep the longest chunk short enough that the join does not delay input or unload. Keep unload on its current path, which cancels prepared work and clears audio, physics, game and render state. If local scratch memory, contention or join time erases the gain, keep the inline reference and drop the prototype. [Unload][unload], [loader acceptance][loader-accept]

## Options and cost

Bevy’s standalone `World`/`Schedule` is a supported API. Bevy v0.20.1 defaults to the multithreaded executor only on non-Wasm targets with both `std` and `multi_threaded` enabled. Otherwise it defaults to the single-threaded executor. The `multi_threaded` feature does not enable the ECS crate's `std` feature. The multithreaded executor precomputes access conflicts (including conditions), starts dependency-ready compatible systems using its compute pool, and honors exclusive and non-send work (the latter uses the local/external executor). Access compatibility prevents overlap, not wrong ordering. Use explicit edges for semantic dependencies and `ApplyDeferred` for command visibility. Ambiguity diagnostics are opt-in and cannot see side effects hidden outside the ECS. [Standalone][bevy-standalone], [executor selection][bevy-kind], [ECS feature flags][bevy-features], [executor source][bevy-run], [thread dispatch][bevy-dispatch], [deferred edges][bevy-deferred], [schedule diagnostics][bevy-settings]

| Option | What Places would pay |
| --- | --- |
| **Unchanged, recommended** | No new dispatch, copying, ownership migration or compile footprint. Direct calls preserve locality and make timing/order straightforward to trace. A hot independent loop would still occupy its calling thread. |
| **One targeted coarse batch, conditional** | Low-to-moderate integration cost and one owner boundary to review. Reuses the current pool and adds no dependency. Prep, scratch working set, cache contention and join must beat inline end to end. Track batch size, bytes, work and wait separately. The inline backend provides a localized rollback. |
| **Explicit native dependency scheduler, defer** | Medium-to-high ongoing cost. A named phase graph can explain edges, waits and queue depths without moving storage, but today’s critical path would still be serial. A dynamic ready queue adds bookkeeping, dispatch and contention to small scenes. Multiple proven jobs would be needed to justify bounded admission, deterministic commits, cancellation and graph diagnostics as a maintained subsystem. |
| **Standalone `bevy_ecs`, reject for this scope** | Wrapping `EntityWorld` as one mutable resource leaves most work conflicting. Real overlap would require splitting or moving storage and reconciling stable IDs, checkpoints and render/audio adapters, or paying for copies and synchronization between owners. Archetype iteration may improve locality for uniform queries, but here it would have to offset that cost plus per-run readiness checks, task wakeups and deferred flushes. Even a minimal build adds Bevy task/platform/util/pointer and ECS proc-macro crates. Reflection, async executor and backtraces are default features, while multithreading is opt-in. Budget competing pools and measure build/dependency cost before any adoption. Neither SDL nor wgpu needs replacement. [Bevy manifest][bevy-manifest], [executor source][bevy-run] |

## Later profile gate

- Use current, compatible non-Backrooms packages. Start with Home (caretaker/carry), Pool (contacts/water), and Performance Lab’s 12 live wanderers and Luau. Add Long Way Home’s Below encounter for Feltling/Guest order and elevator unload. If scope later authorizes controlled counts, use the same editor-authored layout and agent mix at 1/10/50/100 **verified active** actors, within the shared 128 skinned-character cap and spawn budgets (64 action spawns per tick). Warm up after admission. Skip any unsupported count. Renderer-only benchmark extras are not AI. [Environments][environments], [Performance Lab][lab], [Long Way Home][lwh], [limits][spawn-limits], [render cap][char-cap], [benchmark extras][extras]
- Use release binaries on the M2 Pro Mac/Metal and, if available, a Windows x64/DX12 comparison. Record commit, binary and package/asset identities, features, CPU/GPU, cores and actual workers, RAM, OS/driver, display, settings, route/seed and exact timing procedure. Use repeated paired runs with matched fixed delta/input for controlled work and normal delta for live traversal. Disable V-sync and every limiter including `PLACES_BENCH_PACE_HZ`. Log actual mode and physical drawable size and verify cadence is not refresh-capped. A plateau, even with requested Immediate, is inconclusive for presented FPS. Use no-present or heavy tracing only as separate diagnostics. Start with 120 warmup and 1,800 measured frames per steady run, repeated at least three times, and compare inline vs normal worker count. Report mean/p95/p99 frame, update, submit/present and GPU timings, per-phase CPU, prep/join cost, peak memory and input-to-effect latency. [Native runner][runner], [pacing][pacing]
- Use separate bounded traces to compare event/action IDs in order, terminal yield/resume under budget pressure, player/physics acceptance and contacts, trigger paths, pursuit/door/task commits, capture/animation/audio observations, and spawn/despawn. Compare the frame of each effect, as well as final state. Replay rapid cancel/unload/reload, then verify no stale effects and that save/reload follows the existing map contract. Existing action, physics, world and script traces can anchor the comparison. Any missing per-phase or ordering spans are later instrumentation, not existing evidence. Proceed to a separately approved A/B prototype only if visibility is a material CPU cost in realistic runs. Keep it only if its gain exceeds repeat variance in end-to-end frame tails, without small-scene, memory, responsiveness or trace regressions. [Test inputs and receipts][runner], [physics traces][item-step], [world traces][world-trace], [script traces][script-trace]
